# Протокол ручной проверки

Для модератора каталога и для того, кто запускает проверку. Код — `src/attrex/review/` (блок b5).

## Что проверяем

В очередь попадают значения со статусом `review`: каскад нашёл значение, но уверенность ниже порога атрибута,
или значение взято из карточки той же модели (`step = model_match`), а не из текста этой карточки.
Значения `accepted` идут в каталог без проверки, `empty` — в тексте ничего не найдено, проверять нечего.

Порядок — по важности ошибки: сначала карточки с большим трафиком, атрибуты, по которым чаще фильтруют,
и значения с меньшей уверенностью:

```
приоритет = (1 + ln(1 + клики карточки)) × (1 + 1000 × вес атрибута по трафику) × (1 − уверенность)
```

## Шаг 1. Собрать очередь

```
uv run python -m attrex.review.queue --run-id <run_id> --limit 500
```

Файл `outputs/<run_id>/review_queue.csv` открывается в Excel (UTF-8 с BOM). Колонки:

| Колонка | Что это |
|---|---|
| `rank`, `priority` | место в очереди и приоритет |
| `sku_id`, `title`, `category_id`, `clicks` | карточка |
| `attr_id` | атрибут: `color`, `weight`, `cpu`, … (названия — `configs/attributes.yaml`) |
| `value`, `confidence` | что предлагает каскад, в каноне справочника, и его уверенность |
| `value_raw`, `evidence` | как значение написано в тексте и цитата, на которой оно основано |
| `step`, `source` | какой шаг нашёл значение и где: заголовок, описание, другая карточка модели |
| `decision`, `fixed_value` | **заполняет модератор** |

## Шаг 2. Принять решение по каждой строке

Смотрите на цитату `evidence` и при необходимости открывайте карточку на сайте по `sku_id`.

| decision | Когда | fixed_value |
|---|---|---|
| `accept` | значение верно и подтверждается текстом карточки | пусто |
| `fix` | у товара есть значение атрибута, но другое: каскад ошибся в нормализации или выбрал не ту цифру | верное значение в каноне справочника: `черный`, `256`, `6.7` (числа — в единице атрибута: GB, in, mAh, kg, cm) |
| `absent` | в тексте карточки значения нет, а значение каскада взято не отсюда, или атрибут к товару не относится | пусто |

Правила:

- **Решаем только по тексту карточки.** Если значение верно «по жизни», но в тексте его нет — это `absent`:
  каталог не должен содержать характеристик, которые продавец не указал.
- `fix` — только значение из справочника или число с единицей атрибута, без пояснений в ячейке.
- Не уверены — оставьте строку пустой: пустые строки не загружаются и остаются в очереди следующего прогона.
- Строка с неизвестным решением или `fix` без `fixed_value` — ошибка загрузки с номером строки (`rank`),
  а не тихий пропуск.

Примеры:

| value | evidence | Решение |
|---|---|---|
| `черный` (0,70) | «Black» | `accept` |
| `серый` (0,55) | «Titanium Grey» | `accept`: синоним запомнится, и в следующий раз проверка не понадобится |
| `стекло` для `color` | «закалённое стекло» | `absent`: это материал, а не цвет |
| `2000` kg для `weight` | «2т» (грузоподъёмность домкрата) | `fix` → вес из текста, если он там есть, иначе `absent` |
| `apple m1` для `cpu`, step `model_match` | другая карточка модели | `absent`, если в тексте этой карточки процессора нет |

## Шаг 3. Загрузить решения

```
uv run python -m attrex.review.decisions --run-id <run_id> --file outputs/<run_id>/review_queue.csv --reviewer <имя>
```

Решения копятся в `data/processed/review/decisions.parquet`; по паре (карточка, атрибут) действует последнее.
`--to-db` дополнительно переписывает таблицу `rev_decisions` в БД — только когда БД не занята прогоном.

## Шаг 4. Вернуть решения в каскад

```
uv run python -m attrex.review.feedback
```

- **Синонимы.** `accept` и `fix` по справочным атрибутам (цвет, материал, состояние, …) дают пары «написание из
  текста → значение справочника». Они пишутся в `configs/review_synonyms.yaml`; нормализатор берёт их при следующем
  прогоне сам (ручные синонимы из `configs/normalize.yaml` важнее). Написание, по которому модераторы расходятся
  (меньше 80% голосов за одно значение), не записывается.
- **Пороги.** По каждому атрибуту печатается доля `accept`. Если среди 30+ решений модераторы согласны со значениями
  выше медианной уверенности в 95%+ случаев, атрибут предлагается к снижению порога. Решение принимает команда:
  порог задаётся в `configs/pipeline.yaml` (`confidence.thresholds`), а не меняется автоматически.

После этого — новый прогон `scripts/run_pipeline.py`: значения с подтверждёнными написаниями получают больше
подтверждений и чаще проходят порог без проверки.
