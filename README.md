# attrex: атрибуты товаров из текста карточки

Решение команды TushavinClub по кейсу М.Видео. Пайплайн читает карточку товара (заголовок и описание), извлекает
обязательные характеристики её категории, приводит значения к канону справочника и для каждого значения выдаёт
уверенность и цитату из текста, которая его подтверждает. Уверенные значения идут в каталог, сомнительные — на
ручную проверку, решения модератора возвращаются в словари и пороги.

Каскад от дешёвого к дорогому:

```
карточка → 0. категория → 1. схема обязательных атрибутов → 2. правила и словари → 3. парсер «ключ: значение»
         → 4. retrieval к справочнику → 5. калиброванная уверенность → 6. LLM только для остатка
         → 7. значение той же модели (только на проверку) → 8. решение: accepted / review / empty
```

Пример вывода (`scripts/demo.py`, карточка из выборки реальных данных; «эталон» — значение из фида М.Видео):

```
Смартфон Samsung Galaxy S23 128GB Lavender (SM-S911B/DS)
  категория: Смартфоны (источник: feed)
  атрибут                  значение      увер.  статус    шаг     эталон        цитата из текста
  Ёмкость аккумулятора     3900 mAh       0.91  accepted  rules   3900          «3900 мА*ч»
  Бренд                    samsung        1.00  accepted  rules   samsung       «Samsung»
  Модель                   galaxy s23     0.96  accepted  rules   galaxy s23    «Galaxy S23 128GB Lavender (SM-S911B/DS…»
  Диагональ экрана         6.1 in         0.96  accepted  rules   6.1           «6,1 дюйма»
  Объём встроенной памяти  128 GB         1.00  accepted  rules   128           «128GB»
  Цвет                     розовый        0.30  review    rules   лавандовый    «Pink»
```

Спорный цвет не попал в каталог, а ушёл на проверку: продавец написал «Pink», а в справочнике это «лавандовый».

**Как читать результат.** У каждого обязательного атрибута категории — одна строка:

| Статус | Что значит | Что делать |
|---|---|---|
| `accepted` | уверенность не ниже порога атрибута и цитата из текста подтверждает значение | значение идёт в каталог без проверки; порог подобран так, чтобы точность принятых была ≥ 90% |
| `review` | значение найдено, но уверенность ниже порога, цитата не подтвердила его или оно взято у той же модели | модератор принимает, исправляет или отклоняет в интерфейсе проверки |
| `empty` | в тексте карточки значения нет | поле остаётся пустым: значение не выдумываем |

`увер.` — откалиброванная вероятность, что значение верно; `шаг` — кто его нашёл (`rules`, `parse`, `llm`, …);
цитата — фрагмент этой карточки, на котором держится значение. Режим своей карточки (`demo.py --title`) под
таблицей пишет причину для каждого не принятого значения, например «уверенность 0.600 ниже порога атрибута 0.857».

## Кто и как пользуется

| Кто | Задача | Как |
|---|---|---|
| Контент-менеджер каталога | заполнить характеристики новых и старых карточек | полный прогон → файл предсказаний: `accepted` загружаются в каталог, `review` уходят модератору ([Полный запуск](#полный-запуск-на-данных-организатора)) |
| Модератор | проверить сомнительные значения | интерфейс проверки: карточка с подсвеченной цитатой, кнопки «Принять / Исправить / Нет значения»; решения возвращаются в словари ([Ручная проверка](#ручная-проверка)) |
| Разработчик сервиса | атрибуты одной карточки «на лету» | `demo.py --title "…" --description "…" --json` — ответ JSON со значением, уверенностью, порогом, статусом, причиной и цитатой |
| Аналитик | качество и стоимость | `results/README.md` и отчёты `report.md`: P/R/F1 по атрибутам, категориям, продавцам, вклад шагов, ₽ на 1 000 карточек |

## Окружение

Всё ставит [uv](https://docs.astral.sh/uv/) — менеджер окружений Python. Системный Python не нужен: uv скачает
Python 3.12 по `.python-version` и поставит зависимости ровно тех версий, что в `uv.lock`.

```
curl -LsSf https://astral.sh/uv/install.sh | sh                          # Linux, macOS
powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"   # Windows

uv sync --frozen --extra eda --extra llm      # --frozen: строго по uv.lock, без пересчёта версий
```

| Что | Версия |
|---|---|
| Python | 3.12 (поддерживается 3.11–3.13) |
| Ключевые библиотеки (из `uv.lock`) | duckdb 1.5.6, pandas 3.0.6, pyarrow 26.0.0, pydantic 2.14.1 |
| Проверено | Ubuntu 22.04 (ВМ хакатона: 4 ядра, 7,8 ГБ, без GPU), Windows 11 (uv 0.11) |
| Extras | `eda` — ноутбук EDA, `llm` — клиент API для шага LLM, `ml` — локальные эмбеддинги (необязательно) |

Переменные окружения нужны только шагу LLM: шаблон — `.env.example`, без ключа шаг пропускается.

## Быстрый старт: демо за минуту, без данных организатора

```
uv run python scripts/demo.py
```

Данные для демо уже лежат в репозитории: `sample/raw/` — 810 настоящих карточек в формате файлов организатора
(`skus.pkl` 4,2 МБ, `sku_desc.parquet` 330 КБ, `query_clicks.parquet` 92 КБ; контрольные суммы и состав —
[`sample/README.md`](sample/README.md)). Скачивать ничего не нужно; что выборка цела и собирается в БД, проверяет
`uv run pytest tests/pipeline/test_sample.py`. Демо проходит весь путь решения за 10–30 секунд и ~300 МБ памяти
(замер на ВМ хакатона: 10 с, 264 МБ):

1. собирает БД `outputs/demo/attrex.duckdb` тем же кодом, что и на полных данных;
2. прогоняет каскад по всем 810 карточкам, включая карточки без оффера и без категории;
3. печатает три карточки, как в примере выше, и метрики на размеченной части выборки;
4. пишет в `outputs/demo/demo/` файл предсказаний (`predictions.parquet`, `predictions.csv`), отчёт с метриками
   (`report.md`), очередь ручной проверки (`review_queue.csv`) и
   [интерфейс модератора](outputs/demo/demo/review.html) по этой очереди (`review.html`, открыть в браузере).

Своя карточка — атрибуты из произвольного текста:

```
uv run python scripts/demo.py --title "Ноутбук ASUS VivoBook 15 Intel Core i5-1235U 16/512GB серебристый" \
    --description "Диагональ экрана: 15.6 дюйма"
```

Для встраивания в сервис — тот же ответ в JSON (прогресс сборки идёт в stderr, stdout — чистый JSON):

```
uv run python scripts/demo.py --title "Смартфон Samsung Galaxy A55 8/256GB синий" --json
```

Метрики демо иллюстративные: словари строятся по ~400 офферам выборки. Итоговые цифры — в `results/`.

## Полный запуск на данных организатора

Файлы организатора — в `data/raw/`: `skus.pkl`, `sku_desc.parquet`, `query_clicks.parquet`.
Время и память — на 4 ядрах; на ВМ хакатона (7,8 ГБ, без swap) долгие шаги запускать в `tmux`.

Переменные окружения — по шаблону `.env.example` (`cp .env.example .env`). Они нужны только для LLM и
API-эмбеддингов: без ключа эти шаги пропускаются, остальной путь работает. `.env` читают `run_pipeline.py`
и `demo.py` при запуске; уже заданные переменные (на ВМ их задаёт платформа) важнее `.env`. Конфиги `configs/*.yaml` проверяются по схемам `src/attrex/config.py` при каждом запуске;
проверить их вручную после правки: `uv run python -m attrex.config`.

| # | Команда | Что делает | Время, память |
|---|---|---|---|
| 1 | `uv run pytest` | тесты: окружение, схемы конфигов, каждый шаг, сквозной прогон, выборка для демо | 30 с |
| 2 | `uv run python scripts/build_db.py` | `data/attrex.duckdb`: очищенные карточки, эталон в каноне и где он лежит в тексте, схемы категорий, справочники, разбиение | 13 мин при первом разборе `skus.pkl`, далее 6–7 мин; до 4 ГБ |
| 3 | `uv run python scripts/run_pipeline.py --workers 3` | каскад по всем 1,48 млн карточек → `outputs/<run_id>/predictions.parquet` и `pred_predictions` | ≈20 мин |
| 4 | `uv run python scripts/evaluate.py --run-id <run_id> --folds test,holdout_category` | метрики → `outputs/<run_id>/report.md` | 1 мин |
| 5 | `uv run python scripts/export.py --run-id <run_id>` | файл сдачи `outputs/predictions.parquet` и `.csv` | 1 мин |
| 6 | `uv run python -m attrex.review.queue --run-id <run_id>` | очередь ручной проверки (CSV, открывается в Excel) | секунды |

Все итоговые результаты одной командой — прогоны, ablation, метрики, файл предсказаний в `results/`:

```
uv run python scripts/make_results.py
```

Полезные флаги `run_pipeline.py`: `--steps rules,parse` (подмножество шагов для ablation), `--fold valid`
(только часть разбиения), `--limit 1000`, `--hide-category` (проверка шага 0: категория из БД скрыта),
`--raw-confidence` (без калибровки).

Разведочный анализ — `notebooks/01_eda.ipynb`; читать без Jupyter — [`docs/eda/`](docs/eda/README.md) (сводка,
полный текст и графики). Перезапуск: `uv run jupyter nbconvert --to notebook --execute --inplace notebooks/01_eda.ipynb`
(≈15 мин, 3 ГБ).

## Результаты

Итоговый прогон `20261021-0158-full-catalog` на коммите `3eb720b` (текущий `main`): весь каскад по 1,48 млн
карточек, LLM выключен (0 ₽). Метрики — на отложенных частях разбиения, которые не участвовали ни в словарях,
ни в калибровке. Подробно, с разбором — [`results/README.md`](results/README.md); файл предсказаний —
`results/20261021-0158-full-catalog/predictions.parquet`.

| Часть | P | R | F1 | R_text |
|---|---|---|---|---|
| test — известные категории | 96.7% | 46.1% | 62.5% | 82.0% |
| holdout_category — категории, не участвовавшие в подборе | 79.6% | 28.9% | 42.4% | 49.0% |
| обе вместе | 91.2% | 39.5% | 55.1% | 68.8% |

R_text — полнота там, где значение эталона есть в тексте карточки: в тексте лежит только 57% эталона.
Прошлый итог (`20261018-2009`): обе части F1 52,0%, R_text 63,5%, новые категории — F1 34,3%. Рост дали размеры
из описания («Габариты (ШхВхГ): 60х85х60 см»): F1 высоты 32% → 54%, ширины 27% → 44% при точности 95–98%.
Лучше всего извлекаются бренд (F1 83%), модель (81%) и объём встроенной памяти (87%). Калибровка уверенности
поднимает F1 с 33% до 55% при точности около 91%. Каталог «после»: у карточек без оффера (63% каталога) фида нет,
каскад заполняет 38% их обязательных полей. LLM только для цвета на test даёт +0,8 п. п. F1 и +2,1 п. п. F1 по
трафику за 1,99 ₽ на 1 000 карточек — раздел [LLM](#llm).

## Как решение выполняет требования кейса

| Требование кейса | Как выполняем | Где |
|---|---|---|
| На входе только текст карточки | Шаги получают `Card`: заголовок и описание. Поля фида (`vendor`, `model`, параметры) — эталон: в шаги и промпт не попадают | `contracts.py`, CLAUDE.md «Эталон — не вход» |
| Значение в каноне справочника | Числа — в единице реестра (`GB`, `in`, `mAh`, `kg`, `cm`), категориальные — значение справочника `core_ref_values` с синонимами («red», «Красный» → «красный») | `normalize/units.py`, `normalize/values.py`, `configs/normalize.yaml` |
| Уверенность у каждого значения | Подтверждения разных шагов складываются, конкурирующие значения снижают уверенность; изотоническая калибровка по атрибуту и шагу на valid | `confidence/aggregate.py`, `confidence/calibration.py` |
| Не выдумывать | Значение без цитаты из этой карточки не может получить `accepted`; проверка цитаты одна на все шаги и сравнивает после нормализации. Порог «в каталог» по атрибуту подобран под точность ≥ 90% | `normalize/grounding.py`, `pipeline.py`, `configs/calibration.yaml` |
| LLM ограничен схемой и справочником | Ответ по JSON-схеме запроса: у справочного атрибута — только варианты справочника, у числа — число и единица, у значения — цитата. Ответ проходит ту же нормализацию и grounding; не по схеме или без цитаты — отбрасывается | `llm/schema.py`, `llm/extractor.py` |
| Стоимость | Правила закрывают ядро бесплатно; LLM вызывается только для пустого или неуверенного обязательного поля, где в тексте есть зацепка; кэш на диске, жёсткий бюджет в рублях, расход в `pred_runs` | `llm/client.py`, `configs/pipeline.yaml` |
| Все категории и продавцы | Схема обязательных атрибутов строится для каждой из 3,6 тыс. категорий; macro-F1 по категориям; срезы по размеру и сегменту продавца; отложенные целиком категории (`holdout_category`) | `db/build.py`, `metrics/scoring.py` |
| Новые категории | Категория по заголовку для карточек без неё; при неуверенной категории — только сквозные атрибуты; holdout-категории не участвуют в подборе | `category/classifier.py`, `pipeline.py` |
| Метрики по кейсу | P/R/F1 по каждому атрибуту, macro-F1 по категориям, F1 с весом по трафику (клики), вклад каждого шага (ablation) | `metrics/`, `scripts/evaluate.py` |
| Ручная проверка и обратная связь | Очередь: сначала важные по трафику и неуверенные значения; интерфейс модератора с подсвеченной цитатой и подсказками справочника; решения модератора → синонимы в словарь и подсказки по порогам | `review/` |
| Шесть артефактов | код — `src/`, `scripts/`; README — этот файл; EDA — `notebooks/01_eda.ipynb` и [`docs/eda/`](docs/eda/README.md); пайплайн — `scripts/run_pipeline.py`; файл предсказаний — `results/`; презентация — `docs/` | |

## Ошибки и сбои: что происходит

Принцип: сбой одного шага или одной карточки не роняет прогон и не превращается в выдуманное значение. В худшем
случае поле уходит на проверку или остаётся пустым.

| Ситуация | Что делает решение | Где |
|---|---|---|
| Нет БД или файлов организатора | понятная ошибка с командой, которая это исправит (`build_db.py`), и подсказкой про демо без данных | `db/__init__.py`, `scripts/build_db.py` |
| Ошибка в `configs/*.yaml` | запуск останавливается до работы с данными: файл, ключ и что не так (проверка схемами pydantic) | `config.py`, `uv run python -m attrex.config` |
| Нет ключа LLM (`OPENAI_API_KEY`) | LLM-шаг выключается, остальной каскад работает | `llm/client.py` |
| Таймаут, 5xx, обрыв сети у API | повторы с паузой; после повторов — пропуск этого запроса, счётчик сбоев в отчёте; после 10 сбоев подряд LLM отключается до конца прогона | `llm/client.py` |
| Кончился бюджет в рублях | стоимость вызова оценивается до него по худшему случаю; не влезает — вызова нет, поле остаётся с ответом правил | `llm/client.py`, отчёт: «запросов пропущено» |
| Ответ LLM не по JSON-схеме или без цитаты | ответ отбрасывается, значение не принимается (на test: 2,7% ответов не по схеме, 4% значений не прошли цитату) | `llm/schema.py`, `normalize/grounding.py` |
| Значение не подтверждено текстом этой карточки | не попадает в `accepted` ни с какого шага, даже при высокой уверенности | `pipeline.py`, `normalize/grounding.py` |
| Категория не определена или неуверенна (< 0,60) | извлекаются только сквозные атрибуты (бренд, модель, цвет), а не чужая схема | `pipeline.py`, `category/classifier.py` |
| Пустое описание, HTML, длинный текст | описание очищено от HTML при сборке БД; пустое — работаем по заголовку; в LLM — не больше 2 000 символов | `db/build.py`, `llm/extractor.py` |
| Неверные аргументы скриптов | `--fold test` в калибровке, LLM с несколькими процессами, пустой `--title` — отказ с объяснением | `confidence/calibration.py`, `scripts/` |

Цифры — из итогового прогона (`results/`), кроме помеченных как оценка.

| Риск | Что видно сейчас | Мера в решении | Что дальше |
|---|---|---|---|
| **Выдуманные значения** (главный риск LLM) | Точность значений, попавших в каталог: 96,7% на test. Значения, точность которых на valid ниже 90% (вес, большинство цветов), в каталог не попадают. | **Новые категории** | holdout_category: F1 42,4% против 62,5% на известных, точность 79,6% | Категория по заголовку; при неуверенной категории — только сквозные атрибуты (бренд, модель, цвет); отложенные категории не участвуют в подборе | LLM для полей новых категорий: там правилам не на что опереться |
| **Неравное качество для продавцов** | F1 45,3% у продавцов с 1–10 товарами против 63,5% у крупнейших | Срезы по размеру и сегменту продавца в каждом отчёте | Разобрать ошибки мелких продавцов; их написания через проверку — в синонимы |
| **Шумный эталон** | Фасет «разноцветный» при конкретных цветах в тексте; вес и габариты в эталоне расходятся с текстом той же карточки («Вес: 11 кг» при эталоне 7,7 кг); составные фасеты | Заглушки — пропуск, а не ошибка; составной фасет — несколько верных значений; полнота R_text — на парах, где значение есть в тексте | Ручной gold-сет |
| **Карточки без оффера (79% каталога)** | Эталона нет — качество на них не измерено | Те же шаги и проверка цитаты; категория — по кликам или заголовку | Ручная разметка выборки через очередь проверки |

## Файл предсказаний

Одна строка на пару (карточка, обязательный атрибут её категории), включая пустые. Колонки:

| Колонка | Что |
|---|---|
| `sku_id`, `category_id`, `category_conf` | карточка, её категория и уверенность в категории (1.0 — из фида, 0.97 — по кликам, иначе — классификатора по заголовку) |
| `attr_id` | атрибут из `configs/attributes.yaml`: `brand`, `storage`, `screen_diag`, … |
| `value`, `unit` | значение в каноне и единица для чисел |
| `confidence` | откалиброванная вероятность, что значение верно |
| `status` | `accepted` — в каталог, `review` — на ручную проверку, `empty` — в тексте не найдено |
| `step`, `source` | какой шаг дал значение и где в карточке цитата (`title`, `description`) |
| `value_raw`, `evidence` | как значение написано в тексте и цитата-подтверждение |

## Ручная проверка

```
uv run python -m attrex.review.queue --run-id <run_id> --limit 500        # outputs/<run_id>/review_queue.csv
# модератор заполняет колонки decision (accept | fix | absent) и fixed_value
uv run python -m attrex.review.decisions --run-id <run_id> --file outputs/<run_id>/review_queue.csv --reviewer <имя>
uv run python -m attrex.review.feedback                                   # синонимы → configs/review_synonyms.yaml
```

Приоритет в очереди — клики карточки × вес атрибута по трафику × (1 − уверенность). Подтверждённые написания
попадают в словарь нормализатора, и следующий прогон принимает их сам. Когда ставить `accept`, `fix` и `absent`,
с примерами, — [протокол ручной проверки](docs/review_protocol.md).

**Интерфейс модератора** вместо Excel — HTML-страница по той же очереди, открывается файлом, без сервера
([`src/attrex/review/app.py`](src/attrex/review/app.py)):

```
uv run python -m attrex.review.app --run-id <run_id>                     # outputs/<run_id>/review.html
```

На карточке — заголовок и описание с подсвеченной цитатой, значение каскада, уверенность и порог атрибута;
кнопки «Принять», «Исправить» (подсказки из справочника, числа — в единице атрибута) и «Нет значения», клавиши
A / F / X. «Скачать решения» выгружает CSV в формате очереди — его без правок загружает `attrex.review.decisions`.
Без данных организатора: `uv run python scripts/demo.py` и [`outputs/demo/demo/review.html`](outputs/demo/demo/review.html).
Дизайн взят из прототипа `apps/review_prototype/index.html`.

## LLM

По умолчанию выключен (`llm.enabled: false`, `budget_rub: 0`): базовый прогон обходится без него. На один прогон
LLM включается флагом с бюджетом в рублях, конфиг не меняется:

```
uv run python scripts/run_pipeline.py --fold valid --category 761,987 --llm-budget 30 --run-id <run_id>
```

Нужны `OPENAI_BASE_URL` и `OPENAI_API_KEY` (на ВМ хакатона заданы); без ключа шаг пропускается, а не падает.
LLM-прогон — с `--workers 1`: бюджет считается на процесс. Ответ модели ограничен JSON-схемой запроса
(`response_format: json_schema`): у справочного атрибута — только варианты справочника или null, у числа — число
и единица, у каждого значения — цитата. Ответ не по схеме отбрасывается, значение без цитаты из этой карточки —
тоже. Таймаут, повторы и сбои API не обрывают прогон (`llm/schema.py`, `llm/client.py`).

**Где LLM помогает — по замеру.** На valid LLM проверяли на цвете, материале, весе и размерах; по порогу точности
≥ 90% прошёл только цвет: у материала и веса точность подтверждённых значений не дотягивает, размеры модель путает.
Поэтому в конфиге `llm.attrs: [color]`, а значение, подтверждённое LLM, калибруется своей кривой `color/llm`.

Замер на **test** — 4 000 карточек, которые не участвовали в подборе: `20261020-0330-llm-t4000` против того же
каскада без LLM `20261020-0330-nollm-t4000`, отчёт
[`results/20261021-0158-full-catalog/report_llm_test.md`](results/20261021-0158-full-catalog/report_llm_test.md):

| | P | R | F1 | F1 с весом по трафику | F1 цвета | ₽ на 1 000 карточек |
|---|---|---|---|---|---|---|
| без LLM | 97.1% | 41.2% | 57.8% | 37.7% | ≈0% | 0 |
| + LLM для цвета | 96.9% | 42.0% | 58.6% | 39.8% | 12.6% (P 86%) | 1,99 |

В LLM ушли 18% карточек (718 из 4 000), 7,97 ₽ за прогон. Ответов не по JSON-схеме — 2,7%, значений, отброшенных
проверкой цитаты, — 4%. Бюджет прогона отрезал 154 запроса, так что прирост скорее занижен. Честно: точность цветов,
подтверждённых LLM, на test — 86%, ниже целевых 90%; поэтому в итоговом прогоне LLM выключен, а включается флагом
`--llm-budget` там, где +2 п. п. F1 по трафику стоят своих 2 ₽ на 1 000 карточек. Прошлый вариант — LLM на всех
атрибутах смартфонов и ноутбуков — давал +2 п. п. F1 за 15,4 ₽ на 1 000 карточек: в 8 раз дороже.
Расход LLM за всю разработку — 13,8 ₽.
