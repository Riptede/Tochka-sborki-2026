# attrex: атрибуты товаров из текста карточки

Решение команды TushavinClub по кейсу М.Видео. Пайплайн читает карточку товара (заголовок и описание), извлекает
обязательные характеристики её категории, приводит значения к канону справочника и для каждого значения выдаёт
уверенность и цитату из текста, которая его подтверждает. Уверенные значения идут в каталог, сомнительные — на
ручную проверку, решения модератора возвращаются в словари и пороги.

Каскад от дешёвого к дорогому:

```
карточка → 0. категория → 1. схема обязательных атрибутов → 2. правила и словари → 3. парсер «ключ: значение»
         → 4. retrieval к справочнику → 5. калиброванная уверенность → 6. LLM только для остатка
         → 7. значение той же модели (только на проверку) → 8. решение: accepted / review / empty
```

Пример вывода (`scripts/demo.py`, карточка из выборки реальных данных; «эталон» — значение из фида М.Видео):

```
Смартфон Samsung Galaxy S23 128GB Lavender (SM-S911B/DS)
  категория: Смартфоны (источник: feed)
  атрибут                  значение      увер.  статус    шаг     эталон        цитата из текста
  Ёмкость аккумулятора     3900 mAh       0.91  accepted  rules   3900          «3900 мА*ч»
  Бренд                    samsung        1.00  accepted  rules   samsung       «Samsung»
  Модель                   galaxy s23     0.96  accepted  rules   galaxy s23    «Galaxy S23 128GB Lavender (SM-S911B/DS…»
  Диагональ экрана         6.1 in         0.96  accepted  rules   6.1           «6,1 дюйма»
  Объём встроенной памяти  128 GB         1.00  accepted  rules   128           «128GB»
  Цвет                     розовый        0.30  review    rules   лавандовый    «Pink»
```

Спорный цвет не попал в каталог, а ушёл на проверку: продавец написал «Pink», а в справочнике это «лавандовый».

## Быстрый старт: демо за минуту, без данных организатора

Нужен [uv](https://docs.astral.sh/uv/). Python 3.12 он скачает сам по `.python-version`; код поддерживает 3.11–3.13.

```
uv sync --extra eda --extra llm
uv run python scripts/demo.py
```

Демо берёт 810 настоящих карточек из `sample/raw/` (состав и отбор — `sample/README.md`) и проходит весь путь
решения за 10–30 секунд и ~300 МБ памяти (замер на ВМ хакатона: 10 с, 264 МБ):

1. собирает БД `outputs/demo/attrex.duckdb` тем же кодом, что и на полных данных;
2. прогоняет каскад по всем 810 карточкам, включая карточки без оффера и без категории;
3. печатает три карточки, как в примере выше, и метрики на размеченной части выборки;
4. пишет в `outputs/demo/demo/` файл предсказаний (`predictions.parquet`, `predictions.csv`), отчёт с метриками
   (`report.md`), очередь ручной проверки (`review_queue.csv`) и
   [интерфейс модератора](outputs/demo/demo/review.html) по этой очереди (`review.html`, открыть в браузере).

Своя карточка — атрибуты из произвольного текста:

```
uv run python scripts/demo.py --title "Ноутбук ASUS VivoBook 15 Intel Core i5-1235U 16/512GB серебристый" \
    --description "Диагональ экрана: 15.6 дюйма"
```

Метрики демо иллюстративные: словари строятся по ~400 офферам выборки. Итоговые цифры — в `results/`.

## Полный запуск на данных организатора

Файлы организатора — в `data/raw/`: `skus.pkl`, `sku_desc.parquet`, `query_clicks.parquet`.
Время и память — на 4 ядрах; на ВМ хакатона (7,8 ГБ, без swap) долгие шаги запускать в `tmux`.

Переменные окружения — по шаблону `.env.example` (`cp .env.example .env`). Они нужны только для LLM и
API-эмбеддингов: без ключа эти шаги пропускаются, остальной путь работает. Уже заданные переменные (на ВМ их задаёт
платформа) важнее `.env`. Конфиги `configs/*.yaml` проверяются по схемам `src/attrex/config.py` при каждом запуске;
проверить их вручную после правки: `uv run python -m attrex.config`.

| # | Команда | Что делает | Время, память |
|---|---|---|---|
| 1 | `uv run pytest` | тесты: окружение, схемы конфигов, каждый шаг, сквозной прогон, выборка для демо | 30 с |
| 2 | `uv run python scripts/build_db.py` | `data/attrex.duckdb`: очищенные карточки, эталон в каноне и где он лежит в тексте, схемы категорий, справочники, разбиение | 13 мин при первом разборе `skus.pkl`, далее 6–7 мин; до 4 ГБ |
| 3 | `uv run python scripts/run_pipeline.py --workers 3` | каскад по всем 1,48 млн карточек → `outputs/<run_id>/predictions.parquet` и `pred_predictions` | ≈35 мин |
| 4 | `uv run python scripts/evaluate.py --run-id <run_id> --folds test,holdout_category` | метрики → `outputs/<run_id>/report.md` | 1 мин |
| 5 | `uv run python scripts/export.py --run-id <run_id>` | файл сдачи `outputs/predictions.parquet` и `.csv` | 1 мин |
| 6 | `uv run python -m attrex.review.queue --run-id <run_id>` | очередь ручной проверки (CSV, открывается в Excel) | секунды |

Все итоговые результаты одной командой — прогоны, ablation, метрики, файл предсказаний в `results/`:

```
uv run python scripts/make_results.py
```

Полезные флаги `run_pipeline.py`: `--steps rules,parse` (подмножество шагов для ablation), `--fold valid`
(только часть разбиения), `--limit 1000`, `--hide-category` (проверка шага 0: категория из БД скрыта),
`--raw-confidence` (без калибровки).

Разведочный анализ — `notebooks/01_eda.ipynb`; читать без Jupyter — [`docs/eda/`](docs/eda/README.md) (сводка,
полный текст и графики). Перезапуск: `uv run jupyter nbconvert --to notebook --execute --inplace notebooks/01_eda.ipynb`
(≈15 мин, 3 ГБ).

## Результаты

Итоговый прогон `20261018-1104-full-catalog`: весь каскад по 1,48 млн карточек, LLM выключен (0 ₽). Метрики —
на отложенных частях разбиения, которые не участвовали ни в словарях, ни в калибровке. Подробно, с разбором —
[`results/README.md`](results/README.md); файл предсказаний — `results/20261018-1104-full-catalog/predictions.parquet`.

| Часть | P | R | F1 |
|---|---|---|---|
| test — известные категории | 96.5% | 45.1% | 61.5% |
| holdout_category — категории, не участвовавшие в подборе | 75.0% | 22.2% | 34.3% |
| обе вместе | 90.4% | 36.3% | 51.8% |

Лучше всего извлекаются бренд (F1 83%), модель (80%) и объём встроенной памяти (87%).
Калибровка уверенности подняла F1 с 33% до 52% при точности около 90%. Цвет, вес, глубину и процессор каскад
находит, но с точностью 23–80%, поэтому они целиком уходят на ручную проверку, а не в каталог.

## Как решение выполняет требования кейса

| Требование кейса | Как выполняем | Где |
|---|---|---|
| На входе только текст карточки | Шаги получают `Card`: заголовок и описание. Поля фида (`vendor`, `model`, параметры) — эталон: в шаги и промпт не попадают | `contracts.py`, CLAUDE.md «Эталон — не вход» |
| Значение в каноне справочника | Числа — в единице реестра (`GB`, `in`, `mAh`, `kg`, `cm`), категориальные — значение справочника `core_ref_values` с синонимами («red», «Красный» → «красный») | `normalize/units.py`, `normalize/values.py`, `configs/normalize.yaml` |
| Уверенность у каждого значения | Подтверждения разных шагов складываются, конкурирующие значения снижают уверенность; изотоническая калибровка по атрибуту и шагу на valid | `confidence/aggregate.py`, `confidence/calibration.py` |
| Не выдумывать | Значение без цитаты из этой карточки не может получить `accepted`; проверка цитаты одна на все шаги и сравнивает после нормализации. Порог «в каталог» по атрибуту подобран под точность ≥ 90% | `normalize/grounding.py`, `pipeline.py`, `configs/calibration.yaml` |
| LLM ограничен схемой и справочником | JSON-ответ с цитатой, варианты — из справочника, ответ проходит ту же нормализацию и grounding; self-consistency по 3 ответам | `llm/extractor.py` |
| Стоимость | Правила закрывают ядро бесплатно; LLM вызывается только для пустого или неуверенного обязательного поля, где в тексте есть зацепка; кэш на диске, жёсткий бюджет в рублях, расход в `pred_runs` | `llm/client.py`, `configs/pipeline.yaml` |
| Все категории и продавцы | Схема обязательных атрибутов строится для каждой из 3,6 тыс. категорий; macro-F1 по категориям; срезы по размеру и сегменту продавца; отложенные целиком категории (`holdout_category`) | `db/build.py`, `metrics/scoring.py` |
| Новые категории | Категория по заголовку для карточек без неё; при неуверенной категории — только сквозные атрибуты; holdout-категории не участвуют в подборе | `category/classifier.py`, `pipeline.py` |
| Метрики по кейсу | P/R/F1 по каждому атрибуту, macro-F1 по категориям, F1 с весом по трафику (клики), вклад каждого шага (ablation) | `metrics/`, `scripts/evaluate.py` |
| Ручная проверка и обратная связь | Очередь: сначала важные по трафику и неуверенные значения; решения модератора → синонимы в словарь и подсказки по порогам | `review/` |
| Шесть артефактов | код — `src/`, `scripts/`; README — этот файл; EDA — `notebooks/01_eda.ipynb` и [`docs/eda/`](docs/eda/README.md); пайплайн — `scripts/run_pipeline.py`; файл предсказаний — `results/`; презентация — `docs/` | |

## Риски и меры

Цифры — из итогового прогона (`results/`), кроме помеченных как оценка.

| Риск | Что видно сейчас | Мера в решении | Что дальше |
|---|---|---|---|
| **Выдуманные значения** (главный риск LLM) | Точность значений, попавших в каталог: 96,5% на test. Значения, точность которых на valid ниже 90% (цвет, вес, глубина, процессор), в каталог не попадают совсем | Без цитаты из текста этой карточки значение не принимается; одна проверка цитаты на все шаги, включая LLM; LLM выбирает из справочника, отвечает по JSON-схеме, 3 ответа с голосованием; порог по атрибуту под точность ≥ 90% | Прогон с LLM: доля ответов, отброшенных проверкой цитаты |
| **Стоимость на масштабе** | Весь каталог (1,48 млн карточек) без LLM — 35 минут на 3 ядрах CPU, 0 ₽ | LLM только для обязательного поля, пустого или неуверенного после правил, и только при зацепке в тексте; кэш ответов; жёсткий бюджет в рублях на прогон | Оценка: вызов LLM на каждую карточку стоил бы ~0,16 ₽ (≈1 тыс. токенов входа, до 600 выхода, 3 ответа) — ~230 тыс. ₽ за каталог. Замерить долю карточек, которые реально доходят до LLM |
| **Длинный хвост категорий и значений** | macro-F1 по категориям — 59,6%. В справочнике цветов есть редкие «значения» вроде «стекло» и «рисунок»: правила принимают их за цвет | Схема обязательных атрибутов для каждой из 3,6 тыс. категорий; macro-F1 считается наравне с общим | Отсекать в справочнике значения редких фасетов; синонимы из решений модераторов |
| **Новые категории** | holdout_category: F1 34,3% против 61,5% на известных, точность 75% | Категория по заголовку; при неуверенной категории — только сквозные атрибуты (бренд, модель, цвет); отложенные категории не участвуют в подборе | LLM для полей новых категорий: там правилам не на что опереться |
| **Неравное качество для продавцов** | F1 44,9% у продавцов с 1–10 товарами против 57,2% у крупнейших | Срезы по размеру и сегменту продавца в каждом отчёте | Разобрать ошибки мелких продавцов; их написания через проверку — в синонимы |
| **Шумный эталон** | Фасет «разноцветный» при конкретных цветах в тексте; вес и габариты в эталоне расходятся с текстом той же карточки («Вес: 11 кг» при эталоне 7,7 кг); составные фасеты | Заглушки — пропуск, а не ошибка; составной фасет — несколько верных значений | `core_gold.in_text` — где значение лежит в тексте — и полнота на подмножестве, где оно есть; ручной gold-сет |
| **Карточки без оффера (79% каталога)** | Эталона нет — качество на них не измерено | Те же шаги и проверка цитаты; категория — по кликам или заголовку | Ручная разметка выборки через очередь проверки |

## Файл предсказаний

Одна строка на пару (карточка, обязательный атрибут её категории), включая пустые. Колонки:

| Колонка | Что |
|---|---|
| `sku_id`, `category_id`, `category_conf` | карточка, её категория и уверенность в категории (1.0 — из фида, 0.97 — по кликам, иначе — классификатора по заголовку) |
| `attr_id` | атрибут из `configs/attributes.yaml`: `brand`, `storage`, `screen_diag`, … |
| `value`, `unit` | значение в каноне и единица для чисел |
| `confidence` | откалиброванная вероятность, что значение верно |
| `status` | `accepted` — в каталог, `review` — на ручную проверку, `empty` — в тексте не найдено |
| `step`, `source` | какой шаг дал значение и где в карточке цитата (`title`, `description`) |
| `value_raw`, `evidence` | как значение написано в тексте и цитата-подтверждение |

## Ручная проверка

```
uv run python -m attrex.review.queue --run-id <run_id> --limit 500        # outputs/<run_id>/review_queue.csv
# модератор заполняет колонки decision (accept | fix | absent) и fixed_value
uv run python -m attrex.review.decisions --run-id <run_id> --file outputs/<run_id>/review_queue.csv --reviewer <имя>
uv run python -m attrex.review.feedback                                   # синонимы → configs/review_synonyms.yaml
```

Приоритет в очереди — клики карточки × вес атрибута по трафику × (1 − уверенность). Подтверждённые написания
попадают в словарь нормализатора, и следующий прогон принимает их сам. Когда ставить `accept`, `fix` и `absent`,
с примерами, — [протокол ручной проверки](docs/review_protocol.md).

**Интерфейс модератора** вместо Excel — HTML-страница по той же очереди, открывается файлом, без сервера
([`src/attrex/review/app.py`](src/attrex/review/app.py)):

```
uv run python -m attrex.review.app --run-id <run_id>                     # outputs/<run_id>/review.html
```

На карточке — заголовок и описание с подсвеченной цитатой, значение каскада, уверенность и порог атрибута;
кнопки «Принять», «Исправить» (подсказки из справочника, числа — в единице атрибута) и «Нет значения», клавиши
A / F / X. «Скачать решения» выгружает CSV в формате очереди — его без правок загружает `attrex.review.decisions`.
Без данных организатора: `uv run python scripts/demo.py` и [`outputs/demo/demo/review.html`](outputs/demo/demo/review.html).
Дизайн взят из прототипа `apps/review_prototype/index.html`.

## LLM

По умолчанию выключен (`llm.enabled: false`, `budget_rub: 0`): базовый прогон обходится без него. Включение —
в `configs/pipeline.yaml`: `enabled: true` и бюджет в рублях; нужны `OPENAI_BASE_URL` и `OPENAI_API_KEY`
(на ВМ хакатона заданы). Без ключа шаг пропускается, а не падает. LLM-прогон — с `--workers 1`.
