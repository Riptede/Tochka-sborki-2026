# CLAUDE.md

Правила проекта для команды TushavinClub и для Claude. Читать перед любой задачей. Если правило мешает, его меняют здесь
по договорённости команды, а не обходят в коде.

## Задача

Кейс М.Видео: по тексту карточки товара (заголовок, описание, атрибуты продавца) извлечь обязательные характеристики,
привести их к каноническому виду из справочника и для каждого значения дать уверенность. Значение, которого нет
в тексте, не выдумываем. Решение — каскад от дешёвого к дорогому: правила → retrieval к справочнику → LLM только
для остатка → ручная проверка. Оценка: P/R/F1 по каждому атрибуту, покрытие, метрика с весом по трафику, срезы по
категориям и продавцам, вклад каждого шага (ablation), стоимость.

Сдаём шесть артефактов: код, README, EDA, пайплайн, файл предсказаний по каждой карточке, презентацию.

## Нейминг

- Код, идентификаторы, имена таблиц и файлов — английский `snake_case`. Комментарии, docstring, ноутбуки, коммиты — русский.
- **attr_id** только из `configs/attributes.yaml` (`brand`, `storage`, `screen_diag`, …). Русские имена атрибутов фида
  (`Встроенная память (ROM)_search`) встречаются только в `b1` при разборе и в `core_attr_name_map`.
- Единицы в канонической форме реестра: `GB`, `in`, `mAh`, `kg`, `cm`. Числа хранятся строкой в этой единице: `"256"`, `"6.7"`.
- Таблицы БД: `raw_` — как у организатора, `core_` — очищенное и эталон, `pred_` — результаты прогона, `rev_` — ручная проверка.
- Значения перечислений (`step`, `source`, `status`) — только из `contracts.py`.
- Ветки: `b<N>/<коротко>` — `b2/units-regex`, `b3/llm-client`. Коммит: `b2: конвертация единиц памяти`.
- Прогон пайплайна: `run_id` = `YYYYMMDD-HHMM-<коротко>`, например `20261017-1530-rules-only`.

## Контракты

**Вход шага каскада:** `Card` (sku_id, title, description, seller_attrs, category_id, category_conf, category_source).

**Выход шага:** список `Candidate` (attr_id, value в каноне, step, source, score, value_raw, evidence).
`evidence` обязателен для любого непустого значения: это фрагмент текста карточки, который подтверждает значение.
Без него значение не проходит grounding.

**Итог по атрибуту:** `Prediction`, колонки файла — `PREDICTION_COLUMNS`. Файл сдачи — `outputs/predictions.parquet`
и `.csv`, одна строка на пару (sku_id, attr_id) для всех обязательных атрибутов категории карточки, включая пустые.

**БД:** `data/attrex.duckdb`, схема в `src/attrex/db/schema.sql`. Пишет в таблицу только её блок-владелец.

## Что знаем о данных (из EDA, не перепроверять заново)

- `skus.pkl` — xmltodict-дамп YML-фида: 546 тыс. офферов, 6 963 категории (3 599 листовых с офферами). Загружать только
  через `pickle.Unpickler` с запрещённым `find_class` (см. ноутбук, раздел 0.1). Обычный `pickle.load` не использовать.
- Эталон — в фиде. У атрибута два слоя: `Имя_search` — сырое значение (извлекаем), `Имя` без суффикса — фасет для
  фильтров (канон). Имена слоёв совпадают не всегда: `Встроенная память` ↔ `Встроенная память (ROM)_search`. Есть
  имена с пробелами по краям.
- Единица часто лежит в `@unit`, а не в значении: `8` + `ГБ`. Склеивать до любой обработки. 79 атрибутов в разных единицах.
- Заглушки (`другой`, `другие цвета`, `000`, `0`) — пропуск, а не значение. 18% фасетов цвета — заглушки.
- 1P/3P определяем по полю `Продавец`, **не по диапазону sku_id** (он не разделяет сегменты).
- `sku_desc`: 1,18 млн карточек, из них 936 тыс. (79%) без оффера — нет эталона и категории. Категорию берём из
  `sku_seo_id` кликов (совпадает с categoryId в 97%, есть у 6%) или по заголовку (базлайн 93,5%).
- Блоки «Характеристики» / «ключ: значение» есть у 36–38% карточек без оффера и почти не встречаются у офферов.
- Восстановленные и уценённые: описание шаблонное, диагонали и батареи в тексте нет в 100% случаев.
- 22% описаний — дубли; варианты одной модели и дубли держать в одной части разбиения.
- Каталог в основном не электроника: матрасы, чехлы, шторы. Медиана — 10 офферов на категорию.

## Правила работы

- Не выдумывать значения. Значение без `evidence` из текста этой карточки не попадает в каталог. Значение из
  карточки той же модели — только `step=model_match`, с пониженной уверенностью и вне основной метрики.
- LLM возвращает только значения из справочника или число с единицей; вызовы только через клиент `b3` с кэшем и
  лимитом `llm.budget_usd`. Ключи API — в `.env`, никогда в коде и в git.
- Метрики считаются только кодом `b4`. Цифры в презентацию и README — только из прогона с `run_id`; условные цифры
  помечаются как условные.
- Тяжёлые файлы читать потоково или по row group: ноутбук EDA рассчитан на 3 ГБ свободной памяти.
- `data/` и `outputs/` в git не попадают. Большие артефакты (эмбеддинги, индексы) — в `data/processed/`.
- Перед коммитом: `uv run pytest` и `uv run ruff check src tests`.
- Ноутбук коммитим с выводами, если он артефакт сдачи (EDA); рабочие ноутбуки — без выводов.
